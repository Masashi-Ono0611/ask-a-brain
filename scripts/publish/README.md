# Offline publisher operator

This tooling accepts only a deliberately public projection directory. It has no
private-brain connector, source selection, wallet reader, network, registry writer,
or activation command. Run original/private scans outside any AI session. The
five-page fixture is synthetic, not historical evidence or independent supply.

Run with Node 24.13.0 from the repository root. Paths below are placeholders for
operator-owned files; output files must not exist and STAGE must already exist,
be empty, and have canonical real paths (macOS: use /private/tmp, not /tmp).

```
node scripts/publish/operator.ts review MANIFEST PROJECTION WORKSHEET STAGE REVIEW_TXT
node scripts/scan/verify.ts PINS PINS_SHA256 MANIFEST STAGE SCAN_JSON
node scripts/publish/operator.ts seal JOB JOB_SHA256 SIGNED_MANIFEST SEALED_JSON
node scripts/publish/operator.ts list JOB JOB_SHA256 SEALED_JSON PROPOSAL_TXT
```

Review output is JSON-escaped plain text, never rendered Markdown/HTML. Recover
exact UTF-8 strings by strict JSON decoding; read all page, map, policy and metadata
bytes. Review rows have page_id plus nine M07 fields. `derived_from` is always the
literal `founder-private-map`: the actual nonempty evidence references/hashes stay
in the founder's private map, not in this packet. `right_to_sell` is an opaque
attestation ID. Allowed origins are personal-public or synthetic; a prohibited
origin cannot be overridden by an approval label or scan. Whole-page public
download, CC BY 4.0, self-review and recall limitations are explicit.

No approval is generated by these commands. The founder separately records a
PublisherApproval (src/publish/review.ts) after exact-byte/rights/injection review,
including the original-input scan acknowledgment, lineage completeness and a
current source/rights/withdrawal acknowledgment. Approval storage, pins and JOB
must be inaccessible to candidates/agents. Host isolation is a deployment check,
not something a hash proves. Refresh that protected acknowledgment before each
session and within the M03 age bound; a changed acknowledgment needs a new raw
approval-file pin. The founder's protected signing helper supplies the signed
manifest; seal verifies the returned Ed25519 envelope against the pinned key.
There is no signer implementation or private key parameter here. Tests use only
in-memory throwaway keys and simulated human records, not actual human approval.

Hash meanings:

- `manifest_sha256` and PublicApproval.payload_sha256: SHA-256(JCS(manifest payload)).
- ScanAttestation.bundle_sha256: SHA-256(JCS(manifest.files)), frozen wire contract.
- `review_sha256`: SHA-256(JCS(ReviewPacket)); includes all exact public UTF-8 text,
  complete metadata and worksheet. Plain-text escaping is presentation only.
- protected `approval_sha256`, JOB_SHA256 and PINS_SHA256: SHA-256 of exact file
  bytes, including whitespace. Any changed byte requires a new protected pin.
- Inventory hashes: SHA-256 of exact file bytes, without Unicode normalization.
  question-policy.json must be JCS to satisfy both byte and policy hash contracts.

PINS is strict JSON with executable (absolute canonical path), executableSha256,
version, config (absolute canonical path), configSha256. Only the lead supplies
verified scanner version/checksum pins. This task does not invent or download them.
T0's config/tooling-pins.json says 8.30.1 while the design says 8.24.2; reconcile it
before real use. A successful test stand-in does not verify either Gitleaks version.
The controlled config extends built-in rules and adds start/end coverage markers.
No candidate config/ignore file or inherited Gitleaks environment is used. Every
scan runs clean/built-in-secret/clean controls and the independent marker guard;
every exact file is scanned, then bracketed by two checked marker lines, then
scanned clean again. Errors, report absence, warning about skipped bytes, missing
markers and findings block. Raw reports/output stay in OS temp and are deleted.
Manifest metadata is scanned separately; it is excluded from its own inventory.
English/Japanese business/PII patterns are conservative and incomplete; full human
reading and provenance review remain mandatory. Scanner timeout/output bounds
reuse M03 precheckMax/sealedPayloadMax, not additional hardcoded product limits.

JOB is strict JSON with these exact fields (paths are operator-owned):

```
manifest, projection, worksheet, scanner_pins, scanner_pins_sha256,
approval, approval_sha256, signing_key, deployment, seal_actor
```

The first seven fields are strings. signing_key and deployment use wire contracts;
seal_actor must be human for this CLI. The TypeScript API supports test signing
only with synthetic worksheet origins. Both JOB and PINS raw hashes are supplied
from protected operator configuration, never from a candidate's own claims.

`createPublisher` is the protected API. `validateBundle` and `proposeListing`
standalone exports only perform structural/hash verification; they cannot grant a
sealing ticket. `scanAndValidate` authenticates protected approval and fresh rights,
scans, and issues an in-process ticket; `sealBundle` rejects forged/mutated tickets,
rescans and rechecks approval before/after signing. Restarts require validation
again. The protected `proposeListing` method rechecks current authority and scanner.

SEALED_JSON contains only manifest/approval/scans. Its separately mounted projection
is re-inventoried when loading; there is no permissive archive extraction. STAGE
contains only the exact frozen files. Interrupted copies remain inert and cannot be
reused; restart into a fresh empty stage. Previous artifacts are never overwritten.
The proposal is `status: suspended`, `requires_human_repin: true`; founder activation
and registry repin are separate and are intentionally absent from this command.

Host follow-up: verify real pinned scanner controls/coverage report behavior; ensure
source, stage, scanner, rule file and approval files cannot be concurrently replaced
by another principal; exercise actual human key helper and newest source/rights
acknowledgment; run seller/receipt revocation/restore and H1 mount/egress canaries.
Filesystem checks and exact snapshots do not prove isolation from a same-user
process that can race parent-directory replacements. Byte-valid extracts do not
prove usefulness, qualification completeness or absence of arbitrary PII.
