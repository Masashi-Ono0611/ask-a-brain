### Human-only wallet and key procedure

This is the procedure F follows, not instructions for an authoring agent to execute. Unknown wallet/backend support has a **30-minute check U02** in §9; the key boundary is mandatory even if convenient tooling fails. Payment wallets and identity keys are distinct. A signing handle is not permission for the agent to invoke arbitrary signing.

1. **Prepare a human-only environment.** F uses a separate machine or separate OS account/VM that the authoring and runtime agent cannot administer/read. Disable screen capture, screen-history recording, terminal recording, clipboard sync and remote-control/agent sessions for key creation and backup. Close the agent-visible terminal. Do not create keys in this repository, its parent developer account, a shared home folder, `.env`, CI or chat. A same-user permission bit is insufficient. F records only that isolation was checked; agents test access using dummy canaries, never real secret paths/content.
2. **Select and verify tooling before secrets exist.** F obtains a supported Solana wallet/CLI from its official publisher, verifies the release/version and signing workflow with help/documentation, and records public version information. I/R review the adapter and unsigned transaction template using fixtures first. Do not run a remote installation script blindly with wallet access. The official [Solana setup documentation](https://solana.com/docs/intro/installation) links individual installation/help paths; no installer is run by this plan.
3. **Create devnet-only identities privately.** F creates separate buyer Kb-dev, seller Kr-dev and marketplace Km-dev accounts, plus a devnet mint authority if using SPL. All receive addresses must be distinct. Use the wallet's create-new-account/keypair flow in the human-only environment; any seed/key output stays there. Store backups encrypted/offline under F's control. Do not reuse these keys for mainnet. F separately creates offline seal, online application and registry signing identities under C06; the online signer receives its secret directly from F in its restricted runtime, never via an agent-visible command or file.
4. **Share public configuration only.** F supplies public addresses/verification keys and opaque signer handle IDs. In a human-owned policy editor, pin cluster genesis, asset/mint/program/decimals, seller/fee addresses and accounts, endpoint, keys, caps and policy version. I may inspect the public policy export. No seed, key file, mnemonic, exported wallet backup, QR containing a secret, or recovery screenshot crosses into AI context.
5. **Fund devnet privately.** In the human-only wallet/CLI, F explicitly selects devnet, checks its genesis and requests faucet SOL to Kb-dev (and a setup account if required). F creates a six-decimal **TEST** mint and pre-creates all three token accounts using verified tool help; mint enough TEST to cover the documented test budget. Fixture top-ups are recorded as setup, not revenue. F provides public mint/account addresses and setup signatures. Faucet unavailability → use a separately funded devnet test account owned/provisioned by F or record a blocked gate; a local validator is not a devnet substitute. No mainnet funds are used to fix devnet tests.
6. **Validate the signer boundary before funding mainnet.** From TB1 and the authoring account, attempts against dummy signer storage/admin sockets must fail. F authorizes the devnet signer for the versioned broker permit only. Prefer bounded unattended devnet signing if isolation is proved; otherwise F signs each devnet transaction outside the agent and the demo discloses supervised signing. Broker compares returned signed bytes to the armed message, persists them before broadcast and rejects substitution. No `sign arbitrary bytes` MCP tool exists.
7. **Create separate mainnet accounts privately only after Gate 1.** F repeats creation in the human-only environment for Kb-main/Kr-main/Km-main, keeps recoveries offline and does not connect a general savings wallet to the broker. Verify the USDC mint against [Circle's official address list](https://developers.circle.com/stablecoins/usdc-contract-addresses), then RPC owner/program/decimals; never trust a symbol or a seller-provided mint alone. F independently verifies all recipient addresses on the wallet display.
8. **Fund only the authorized exposure.** F personally transfers the single purchase amount (proposed 0.01 USDC) and a separately itemized SOL setup/fee allowance from an existing wallet/exchange; setup creates recipient token accounts in advance. Before funding, F reviews actual account-creation costs and approves a public funding worksheet with asset quantities, fee ceiling and setup allowance. Do not invent a required SOL deposit. After setup, remove surplus buyer spendable balance through F's wallet if needed; leave purchase principal plus ≤100,000 lamports transaction-fee allowance under the broker's one-purchase policy. Native-SOL fallback instead funds exactly its approved 1,000,000-lamport purchase plus fee allowance. Setup and surplus movements are human-operated transactions, disclosed separately.
9. **Approve the purchase at runtime, once.** On the protected human screen F reviews network/genesis, exact mint/asset, total, 90/10 amounts, both recipients, maximum/estimated network fee, quote/manifest/policy hashes, message digest and expiry. An explicit one-use approval binds that message; replays/replacements require reconciliation and, for a new message, fresh approval. Sign privately, return only signed transaction/public signature. No blanket “approved in design” or devnet approval applies. After one success, mainnet mode locks; another take for video uses the recording, not another purchase.
10. **Close and recover.** F verifies finalized balance deltas/receipt, revokes temporary signer capabilities and moves remaining test funds manually if desired. Kr/Km private keys never enter services; refunds are human wallet actions with separate mainnet approval and separate signatures. Lost key/possible exposure → stop, human rotation and public-key repinning; agents never inspect the suspect secret. No mainnet negative-control attack is permitted.

Solana instructions in one transaction are atomic but failed transactions can still consume network fees; devnet atomicity tests must show principal and fees separately. This property is documented by [Solana transactions](https://solana.com/docs/core/transactions), not evidence that our implementation works.

## 3. Positive-control plan for EVERY guard.

**Doctrine:** a guard is `UNVERIFIED` until its rejection is observed in an isolated safe setup, its admissible counterpart succeeds, and state restoration is evidenced. A test that merely asserts a branch exists, a screenshot of a green badge or an unexecuted fixture is insufficient. All guards in §2 and the adopted 01/02/04 contracts map below; adding a new guard requires adding its control before calling it verified.

Use synthetic public fixtures in a disposable namespace, no live brain/production keys/mainnet RPC. Crypto fixtures contain only public keys/messages/signatures supplied as public test vectors or through F's isolated test signer; agents do not generate/read private keys, including test keys. Test-only adapters are absent from release artifacts. Before each exercise save clean fixture/policy/DB digests and baseline counters. ## 4. Avoided-loss replay evaluation.

Execution implements the estimand in **02 §7** and comparison in **01 §10**. It tests whether consulting this frozen knowledge product changes completion of these historical personal tasks. It does not establish marketplace necessity, future generalization, willingness to pay, safe arbitrary-agent autonomy or seller expertise.

### Incident schema and selection

Each case is a versioned record with the following required fields. Original private records never enter the repository, seller host or hosted model.

**Thirty-minute inventory, then preparation:** F privately scans only an explicitly selected personal harness record directory and writes a candidate index of opaque IDs/date/failure category/eligibility evidence. Do not search the whole gbrain or all work histories for convenient failures. Predetermine a time window (proposed latest 90 days ending Oct 8), chronological order and at most one incident per root-cause episode. Choose the first ten eligible reconstructible incidents in that order. Freeze the candidate ledger, exclusions and selection rule **before** seeing treatment results. If fewer than ten survive, use all eligible cases and report actual n/Gate 2 shortfall; do not silently widen the window or replace hard cases. Any pre-run expanded window is a dated protocol amendment.

Eligible: an actual personal toy/project/harness operation with a recorded before-state, observed failure, right to reuse the material, and a safe reproducible failure predicate. Potential categories, **not claims these records exist**: missed completion check, incorrect retry after timeout, unsafe cleanup of a disposable artifact, premature “done” report, stale local state. Incident category diversity is reported, not manufactured through quotas.

Forbidden sources: employer/Org or client incidents, customer/member records, private team/community messages, third-party conversations, production financial actions, downloaded public incident datasets, someone else's examples, dream-generated summaries, invented failures labeled historical, or incidents recovered by querying private business material. A harness log can contain work data even if the harness is personally owned. Mixed-origin/uncertain logs are excluded wholesale. Personal-only transcript evidence may be inspected privately by F for historical verification; raw transcripts and transcript-derived pages never become the sellable slice (00a P1; 04 A1). Agents receive only newly prepared approved fixtures.

F removes credentials, usernames, hostnames, internal paths, contact details, wallet identifiers and unrelated text from **eligible** records, substitutes dummy identifiers consistently, recreates a minimal toy environment and checks failure fidelity. Preserve relevant ordering, tool errors and constraints; if these cannot be preserved safely, exclude. Hash original records only in a private provenance map; public references are random IDs, not hashes of guessable private data. Run G10–G13 on release fixtures and have F read the entire final projection. R reviews only those public-safe projections. No cloud “redaction assistant” sees original records.

### Paired protocol and determinism

1. Before the primary run, freeze ten-or-actual-n case IDs, rubrics, generic slice, question approvals, model/prompt hashes, image/tool fixtures, budgets and scorer. F and R check overlap: exact incident narrative, hidden criterion or its case-specific solution in the slice → mark contaminated and exclude from primary n **before running**, retaining it separately. Generic lessons learned after the historical incident are allowed only with explicit hindsight disclosure; this is not a time-travel prediction claim. Do not author pages to fix a failed treatment after seeing results.
2. Create two clean identical snapshots per case. Both arms have the same task prompt, safe local tools, pre-action observations and existing completion gates. Never turn off a mandatory baseline safety check to make the treatment look useful. Baseline has no consult; treatment is offered at most one `consult`, with the same goal and a frozen safe-question policy. No mandatory prompt saying “use this answer to pass criterion X.” Non-use, abstention, delivery failure and timeout stay in the treatment denominator (intention-to-treat).
3. **Chosen budget profile:** ≤10 minutes wall time, ≤8,000 buyer-model tokens, ≤30 local tool calls per arm; treatment's consult counts as one tool call, its latency is inside 10 minutes and answer tokens consume buyer context. Seller preparation compute is additional, explicitly measured, and bounded separately; do not claim equal total compute. Devnet payment cap is one quote at the technical-test listing price plus 01's separate network-fee cap. Identical baseline budget permits extra local reasoning with time unused by consulting. If historical fidelity needs a different profile, freeze it per case before either arm runs and disclose the difference.
4. Pin a provider model snapshot where offered, temperature 0 and seed where supported; never imply these make hosted models deterministic. Use the same prompt bytes except consult availability, fixed mock clock/input files and deterministic safe tool responses; no browsing, live remediation, unrestricted filesystem or chain transaction tools for the agent. Isolated broker handles devnet only. Alternate run order A/B then B/A by selection index, with a fixed recorded shuffle seed for case order. Separate conversations, caches, IDs, volume and process state; no cross-arm memory. Actual chain finality remains variable, measured inside treatment latency.
5. Record complete **sanitized-fixture** transcripts including prompt/tool/model response, model identifiers/parameters, timestamps, tool exit codes, final environment tree, guard decisions, consult/receipt/signature and token usage. Hash artifacts at capture; R receives immutable copies. Provider timeouts count as attempts. Retain all attempts with status; never rerun an unfavorable answer alone. If infrastructure prevents both arms starting, record unresolved. One predeclared whole-pair retry may be scheduled after restoration, reported separately; primary result retains the original outcome/unknown. Optional second pairs for every case use a second fixed seed and are secondary robustness evidence; if cut, state “one pair per case.”
6. Each answered treatment uses the actual devnet protocol including finality/reveal/receipt; simulation/debug playback is labeled and excluded from live-payment counts. No real-money experiment is needed for ~10 cases. Within the stricter quotas C03, schedule ≤10 unique founder prechecks/seller/day; the 10-minute duplicate cache may assist debug but never conceal a new paid attempt. Optional repeated pairs must fit a later day's quota and budget; do not invent extra buyer identities to evade caps.

### Judging, operational verdict and reporting

R creates blinded packets with randomized A/B labels and stable final-state/action evidence; remove receipts, seller names, consult markers and incidental wording that reveals the arm without removing task-relevant behavior. Keep originals for audit. Deterministic checkers run independently of the agent. Two judging passes (Claude review and F) apply the frozen rubric without seeing the pair mapping or aggregate result; F knows the historical event and is not independent. R may also recognize its own protocol. Record blinding guesses and leakage, label any unblinded subjective verdict accordingly. An optional uninvolved human can adjudicate disagreements; if unavailable and objective evidence does not decide, mark **unresolved**, not founder-favored success. Do not claim two independent human judges.

For each arm, `PASS` means the named target failure did not occur **and** the positive task/safe-stop criterion was achieved by budget end, with required evidence and no critical regression. A safe stop counts only when the rubric predeclared it as the correct goal; doing nothing forever is not prevention. `FAIL` means observable target failure, task failure, critical new harm, or budget exhaustion without the required terminal state. `UNKNOWN` means missing/corrupt observation prevents judging; an observable ordinary timeout is a failure, not an unknown chosen to soften the result.

**Avoided:** baseline FAIL and consulted PASS, with trace evidence that the cited intervention was available before the changed action and all predicates verified. Baseline FAIL / consulted PASS without an attributable consult (e.g. treatment never called it) is reported as an unexplained paired improvement, not credited to avoided loss. **Regression:** baseline PASS / consulted FAIL. Also show both PASS, both FAIL, and any UNKNOWN. Report both raw contingency cells and the stricter attributed avoided count. `net attributed prevention = attributed avoided − regressions`; never discard a regression for being inconvenient. **No fractional prevention credit.** A predeclared secondary checklist can show “2 of 3 steps improved” or measured remediation minutes, but it contributes zero to the binary avoided count unless all required criteria pass.

One-page output: total candidate count; exclusions by reason; primary n and synthetic/contaminated counts separately; number of attempted/completed/unknown pairs; four pass/fail cells plus unknowns; attributed avoided, unexplained improvements, regressions, net; refusals, consult non-use, failed delivery; measured per-case wall time, human active remediation time (if observed), buyer/seller tokens and spend; median/min–max of observed paired times with their denominators. Always report adverse incidents and unresolved refunds. Use **counts, not percentages**, no significance/power claims, no population projection or annualized savings. Show TEST principal and devnet SOL fees as test units, actual model/hosting expenses separately. Currency value follows 02 §7 only with observed human time and declared wage/FX assumptions; otherwise report minutes/native units. No historical loss is “saved cash” merely because a toy replay passes.
