## Q1–Q9 required decisions

### E01 / Q1 — Which Solana SDK family?

- **Status:** provisional, founder may overrule.
- **Question:** Which family safely supports one legacy transaction with two TransferChecked + Memo, signing, broadcast and independent exact verification within four days?
- **Options considered:** `@solana/kit@8.4.0` plus its compatible token/instruction packages; `@solana/web3.js@1.99.0` + `@solana/spl-token@0.4.15`; mixing Kit with web3-oriented SPL helpers.
- **Decision:** web3.js + spl-token only, exact pins above; SDK values stop at the `chain` boundary.
- **Rationale:** Familiar Transaction/Message/keypair and SPL decode APIs reduce code-generation/review risk. Whole-message reserialization and explicit instruction checks suit the fixed legacy rail. Kit is modular and attractive for smaller browser bundles; this backend has no bundle-size target. Do not mistake web3's maintenance status for a future-growth recommendation or its familiarity for correctness. Mixed families add conversion/signing surfaces with no required benefit.
- **Verification / reversal trigger:** T0/T2 lead verifies peers, script-free pure-JS import/sign/serialize/decode/verify, exact account metas and known vectors. Reverse only if selected versions cannot satisfy these checks or a relevant security/license blocker remains; revalidate all wire/chain contracts and Gate1 on any family change. No alternate payment rail.

### E02 / Q2 — TypeScript 7.0.2 or a conservative compiler?

- **Status:** provisional, founder may overrule.
- **Question:** Does registry availability justify pinning TS7 for Node type stripping and type checking?
- **Options considered:** supplied `typescript@7.0.2`; an unverified 6.x patch; consultant's 5.8.3; verified stable release-line 5.9.3.
- **Decision:** `typescript@5.9.3` and `@types/node@24.0.0`, NodeNext/strict/noEmit/erasableSyntaxOnly and explicit `.ts` imports. Do not use Node26 types just because 26.6.4 is available.
- **Rationale:** Node executes erased TS independently of the checker. TS7 availability does not prove packaging/install/API compatibility; the deadline does not justify introducing that uncertainty. 5.9.3 keeps the familiar compiler and supports the needed flags. Node-major-matched types limit accidental runtime-only-in-26 APIs. [Microsoft release evidence](https://github.com/microsoft/TypeScript/releases) supports 5.9.3's existence, not this project's full dependency compatibility.
- **Verification / reversal trigger:** Lead checks registry, actual declarations and tsc+Node import/SQLite/SDK smoke with scripts disabled, no skipLibCheck blanket. Pins' exact compatibility is **UNVERIFIED**. If a required dependency cannot typecheck, first choose the smallest compatible dependency/type patch; change compiler only with a recorded passing smoke, not an automatic latest upgrade.

### E03 / Q3 — SQLite driver and experimental warning?

- **Status:** provisional, founder may overrule.
- **Question:** Use experimental platform SQLite or a native module that may require lifecycle builds?
- **Options considered:** `node:sqlite`; better-sqlite3/sqlite3-style native dependencies; external DB/ORM.
- **Decision:** pinned Node24 `DatabaseSync` behind role-local `Store`; retain experimental warning on stderr. WAL/FULL durability, foreign keys, busy timeout, short synchronous transactions, versioned migrations and expected-version writes.
- **Rationale:** No native installation scripts, no service/ORM, adequate local bounded throughput. Experimental risk is contained by exact runtime pin and adapter; a warning is neither an error nor grounds to suppress all warnings. MCP stdout remains protocol-only.
- **Verification / reversal trigger:** T0/T3 crash/rollback/concurrent-reservation/restore probes must pass. Unknown schema or missing DB durability blocks signing. Later stable Node SQLite or reviewed replacement driver may replace adapter after quiescing/reconciling money, backup/tombstone preservation and migration tests. No live migration while signed transactions are ambiguous.

### E07 / Q7 — Exact-message human signing from CLI keypair file?

- **Status:** provisional, founder may overrule.
- **Question:** How can human file signing remain small/testable while keeping runtime agent away from the key and preserving approval order?
- **Options considered:** run solana CLI; broker directly opens real key; same-user child wallet; separate terminal helper with restricted IPC and durable sign-only journal.
- **Decision:** HumanCliSigner is a broker-side IPC adapter to a protected human-operated Node helper. Only helper receives founder's path privately; validate standard 64-byte keypair JSON. Human reviews offer before arm, then helper independently decodes/displays frozen armed message and requires `approve <sha256>` from controlling TTY. It signs/journals but never broadcasts; broker verifies/journals before broadcast. TestSigner implements same port and automatic **test** approval only on pinned devnet/local simulation.
- **Rationale:** No CLI installation or wallet UI framework; exact bytes and TTY confirmation are testable. Isolated key ownership plus immutable-message recovery is stronger than trusting an agent-visible approval flag. Missing signature return remains pending until recovered/expired conclusively, never silently rebuilt.
- **Verification / reversal trigger:** Founder exercises helper on throwaway devnet key for Gate1(f); substitution/expiry/journal failure/control tests must pass. TestSigner alone is insufficient. If helper cannot provide sign-without-broadcast and durable same-message recovery, paid mode blocks; real keys never enter authoring tools to debug it.

- **L6 measured Codex 0.160.0 tool surface (2026-10-09, lead, trusted instrumentation)**: Codex was pointed at a local mock Responses endpoint (`docs/evidence/replay/mock-responses-endpoint.cjs`, clean CODEX_HOME, no credentials) that records the exact request body, whose `additional_tools` item is the complete model-visible tool list. Default surface: top-level `exec` (a JS orchestrator that nests `apply_patch`, `exec_command`, `write_stdin`, `view_image`, goal tools, `clock__curr_time`), `collaboration.*` (spawn/send/wait/interrupt/list/followup), `request_user_input(_async)`, `wait`, `clock.sleep`. `--disable shell_tool` removes `exec_command`/`write_stdin`; `--disable goals` removes the goal tools; `--disable sleep_tool` removes `clock.sleep`. NOT removable by any config key accepted under `--strict-config`: `exec` itself, `apply_patch`, `view_image`, the collaboration tools, `request_user_input`. Consequence: the T7/M10 requirement "exactly 5/6/10 tools" cannot be met with this CLI; amended protocol (frozen before outcomes): all arms share the SAME residual built-in surface (symmetry), effectful built-ins are neutralised (no shell; read-only sandbox so `apply_patch` cannot write; no network), the arm-specific MCP tools are the only tools with task effect, and the complete captured inventory per arm is stored as evidence. `view_image` (reads image files anywhere readable) and subagent spawning remain residual risks and are reported, not claimed away.

- **L8 primary study result and the labelled secondary variant (2026-10-10, lead; provisional, founder may overrule)**: the pre-registered 18-attempt primary study ran to completion at revision a707628 (model gpt-6.1-sol, effort medium, host-mode, C simulated). Result: I2 and I6 pass in all three arms; I1, I4, I5, I8 fail in all three arms with REQUIRED_COMPLETION_MISSING. Offline replay of every admitted call through the same fixture engine shows these are completion-gate denials (PRECONDITION_REQUIRED on a fix, then EVIDENCE_DENIED / TERMINAL_EVIDENCE_REQUIRED / OWNERSHIP_EVIDENCE_REQUIRED on finish_with_evidence) that the agent could not see because every denial returned the bare string REQUEST_DENIED. B and C did receive their knowledge (checklist 8.6k chars / consult answers ~3k chars). Reading: no A/B/C difference detected, with a floor effect on four incidents caused by uninformative tool errors; this says nothing about whether consultation helps. The primary results stay exactly as recorded (all attempts count). Pre-registered secondary variant (decided before its results exist): rerun the same 18 slots in the same rotation with request flag `error_codes=true`, which lets the supervisor return ONLY allowlisted procedural denial codes (PRECONDITION_REQUIRED, INSPECTION_REQUIRED, EVIDENCE_DENIED, TERMINAL_EVIDENCE_REQUIRED, OWNERSHIP_EVIDENCE_REQUIRED, STALE_VERIFICATION, FIX_DENIED, TASK_CLOSED) as `REQUEST_DENIED:<CODE>`; rubric text never passes. The variant is post-hoc (motivated by the primary result), is reported separately and labelled, and never replaces or is pooled with the primary outcome.
